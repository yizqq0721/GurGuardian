> 编写日期：2026-10-25。用途：指导赛前开发、验证、材料准备与答辩。
> 依据：`FurGuardian-系统介绍.md`、`比赛要求整理.md`、README，以及营养引擎、Agent 编排、工具上下文、计划保存和确认服务的代码抽查。
> 本文是实施建议，不代表以下规划已经实现。未实际运行系统、核验线上版本或检查鸿蒙源码；鸿蒙现状以团队提供的系统介绍为依据。

## 1. 总体判断与目标

FurGuardian 已具备较好的工程基础：独立营养算法、宠物数据积累、知识检索、工具型 Agent、人工确认写操作、多端访问。后续目标应是把这些能力组织成一个评委可以连续验证的场景，并补齐效果与可靠性证据。

推荐核心定位：

> 面向犬猫主人的日常照护助手：营养数字由算法计算，照护分析由多个职责清晰的 Agent 协作完成，建议附事实与来源，行动计划由主人确认执行，并在鸿蒙真机完整使用。

其中“多个 Agent 协作”必须等实现和评测通过后再写入正式介绍。

赛前优先级：

| 优先级 | 工作 | 原因 |
| --- | --- | --- |
| P0 | 最新版本上线、权限与数字正确性、超时控制、演示证据、官方规则核对 | 决定能否稳定提交和兑现材料承诺 |
| P1 | 最小多 Agent 协作、可见协作轨迹、评测集、鸿蒙演示强化、真实试用 | 提升技术表达和项目说服力 |
| P2 | 鸿蒙原生通知或桌面入口、知识管理、数据导出等 | 根据剩余时间与真实需求选择 |
| 暂缓 | 图片识病、自动诊疗、大规模社交商城、复杂自治 Agent 群 | 偏离当前场景，验证成本高 |

## 3. 多 Agent：建议采用的最小方案

### 3.1 什么才算真实协作

把同一个提示词拆成几个标题、给工具换成“Agent”名字、让一个模型分别扮演三个人，都不足以证明系统层面的协作。

本方案要求：不同角色具有独立任务和可调用工具范围；协调者生成受约束任务；专项 Agent 独立调用模型并返回结构化结果；后续步骤实际使用前序结果；全过程有可复核记录。多个角色可以共用同一个模型服务，无需因此引入不同厂商或微服务。

这一设计是可解释的工程方案，是否符合赛事的多 Agent 认定仍以官方口径为准。

### 3.2 推荐三个角色

| 角色 | 职责 | 允许使用的能力 | 输出 |
| --- | --- | --- | --- |
| 照护协调 Agent | 理解问题、拆任务、选择路径、整合结果 | 专项任务委派；受控计划生成入口 | 任务计划、最终回答、行动提案 |
| 营养分析 Agent | 分析已记录喂食与体重，解释算法结果 | 档案、体重、喂食、确定性营养计算 | 事实、数据缺口、带依据的发现 |
| 照护计划 Agent | 检查提醒、依据知识提出可执行步骤 | 档案、提醒、知识检索 | 待办发现、来源、行动候选 |

安全审核首先做成确定性校验器：检查事实引用、日期、权限和计划字段。暂不增加第四个模型调用，以控制延迟。若后续确需模型做语义复核，使用单独、可开关的审核步骤，并测量收益。

营养分析 Agent 不计算热量、克数或变化率；这些数字来自业务服务和营养引擎。照护计划 Agent 不推断疫苗或驱虫的个体医疗安排，只整理用户已有计划、解释可用资料，必要时请求补充信息。

### 3.3 一个真实协作案例

用户：“看看团团这周照顾得怎么样，下周有哪些事要做？”

1. 服务端校验用户与宠物归属，固定当前时间和查询范围。
2. 协调者生成任务：营养分析、照护计划；使用枚举任务类型与有界参数。
3. 营养分析 Agent 查询体重、打卡和营养方案，返回本周记录及缺失项。
4. 照护计划 Agent 获取提醒，并读取前一步的发现，补充对应知识和下一周行动候选。例如“记录不足”对应补记提醒，而非直接认定漏喂。
5. 校验器确认每个事实 ID 存在，数字和单位一致，缺失维度未被补成确定结论。
6. 协调者基于通过校验的结果生成总结：已有记录、无法判断的部分、下一步行动。
7. 用户要求创建提醒时，再生成服务端待确认计划；用户点击确认后写入。

这里的协作价值在于结果交接：照护计划使用营养分析发现的数据缺口，最终回答使用两者的证据。不能只展示两段互不相关的回答。

### 3.4 路由要体现取舍

| 问题类型 | 建议路径 |
| --- | --- |
| 简单知识科普 | 知识检索与一次回答，无需调用全部角色 |
| 本周喂食或体重 | 营养分析角色，必要时补知识 |
| 综合照护与下周安排 | 协调者 → 两个专项角色 → 校验 → 汇总 |
| 明确新增提醒 | 参数提取 → 校验或澄清 → 待确认计划 |
| 紧急症状 | 现有红线流程优先，停止常规规划 |

先采用顺序编排，便于复用现有上下文；后续确认分支完全独立、上下文已隔离后再并行。不要为了展示协作，让所有请求固定经过三个模型。

## 4. 多 Agent 的代码落地

### 4.1 建议新增与调整的位置

以下类名均为建议，不代表已有代码。

| 文件或组件 | 作用 |
| --- | --- |
| `pet-ai/.../orchestration/PetCareOrchestrator.java` | 统一请求预算、任务调度、结果交接与回退 |
| `pet-ai/.../orchestration/TaskPlanner.java` | 将协调者计划解析为受限任务类型 |
| `pet-ai/.../specialist/NutritionAnalyst.java` | 独立角色提示词、工具集与输出解析 |
| `pet-ai/.../specialist/CarePlanner.java` | 独立照护角色与前序发现输入 |
| `pet-ai/.../model/AgentTask.java` | 类型、时间窗、依赖任务 ID |
| `pet-ai/.../model/AgentFinding.java` | 发现、事实 ID、来源 ID、数据完整度 |
| `pet-ai/.../validation/EvidenceValidator.java` | 引用、数字、缺失和计划校验 |
| `pet-ai/.../trace/AgentRunTrace.java` | 保存角色、步骤、状态、耗时及摘要 |
| `pet-web/.../AiController.java` | 保留入口，委派编排服务并映射响应 |
| `fur-guardian-front/src/views/KnowledgeView.vue` | 展示角色步骤、依据、缺失和行动卡 |

原有 `PetAgentService` 可保留为兼容路径，通过配置开关启用新编排。不要同时重构登录、数据库和全部问答接口。

### 4.2 结构化事实优先于自然语言

当前工具主要返回字符串，建议先在业务层增加结构化结果，再按需生成给模型阅读的摘要。例如：

```json
{
  "taskId": "nutrition-1",
  "status": "PARTIAL",
  "window": {"start": "2026-10-19", "end": "2026-10-25"},
  "facts": [
    {"id": "feeding.recordedDays", "value": 5, "unit": "day"},
    {"id": "feeding.windowDays", "value": 7, "unit": "day"}
  ],
  "findings": [
    {"code": "RECORD_GAP", "factIds": ["feeding.recordedDays", "feeding.windowDays"]}
  ],
  "missing": ["actualIntakeOnUnrecordedDays"],
  "sourceIds": []
}
```

模型可解释“记录覆盖不足”，不能据此写成“两天没喂”。面向用户的数字尽量由服务端模板或事实绑定组件展示；自由文本中的数字校验只能辅助发现问题，不能作为语义正确的完整证明。

专项角色输出必须经过 JSON 解析与字段验证。解析失败只允许在剩余预算内进行一次修复，仍失败则返回已有事实卡片，不把未校验内容直接作为行动依据。

### 4.3 权限与上下文

当前 `AgentContext` 使用 `ThreadLocal`，其状态包含可变列表，不能直接复用为并行任务共享上下文。

改造原则：

1. 由服务端创建不可变 `RequestContext`：用户、宠物、请求 ID、当前时间、截止时间。
2. 模型生成的任务参数只允许任务类型、查询天数等白名单字段；用户与宠物 ID 由服务端注入。
3. 每个角色使用独立状态，子任务完成后返回不可变结果，由协调层合并。
4. 继续保留业务服务层归属校验，不能依赖模型或协调者检查。
5. 循环委派、无限任务和任意 URL 工具调用均不开放；限制任务数、依赖深度、工具次数与模型次数。
6. 用户输入、历史消息和检索文档视为数据，不能通过其中的指令扩大工具权限。

### 4.4 输出与轨迹

响应可逐步增加 `requestId`、`mode`、`agentSteps`、`facts`、`missingDimensions`、`validationStatus`、`pendingAction`，兼容现有字段。

前端步骤示例：

```text
任务拆解：检查本周营养记录与未来待办
营养分析：已读取体重和喂食，发现记录缺口
照护计划：已核对提醒，并补充记录建议
依据校验：通过；实际摄入量资料不足
行动：已生成补记提醒计划，等待确认
```

展示可核对的动作、结果与耗时即可，不展示或伪造模型内部思考过程。只有后端实际进入某步骤后才能显示“执行中”，不能用定时动画假装真实进度。

## 5. 先修复现有可靠性问题

### 5.1 总超时与后台任务

代码抽查发现 `PetAgentService.invoke` 每次可等待 50 秒，强提示重试会再执行一次；随后控制器还可能走 RAG。因此“整体 50 秒超时”的文档描述与实现不一致。

建议：请求入口设一个绝对截止时间，规划、专项调用、修复和回退都使用剩余预算。预留时间返回事实卡片，不在预算耗尽后再启动一次完整模型调用。以下是初始设计预算，需实测调整，不能对外当作已达到性能：

| 环节 | 初始预算 |
| --- | --- |
| 路由与任务规划 | 最多 5 秒 |
| 专项查询与分析 | 合计最多 20 秒 |
| 校验与汇总 | 最多 10 秒 |
| 回退和响应余量 | 5 秒 |
| 整体目标 | 40 秒以内结束或明确返回部分结果 |

当前 `CompletableFuture.get` 超时不会自动停止后台任务。需使用有界执行器、底层 HTTP 超时与可用的取消机制，停止继续调度；单独调用 `cancel` 不保证中断底层网络请求。记录未结束任务与模型请求数，验证超时后没有持续扩散。

### 5.2 计划持久化与幂等

当前 `AgentPlanStore` 为进程内 Map，只能在当前实例和有效期内提供已有设计中的重复确认效果。重启会丢失计划，多实例也不共享状态。

建议增加 `agent_action_plan` 表，至少包含：token 哈希、用户、宠物、类型、规范化参数、状态、失效时间、结果 ID、创建时间。token 使用安全随机值，日志不记录完整 token。

确认时在同一个数据库事务内锁定计划或条件更新状态，再创建提醒并保存结果。使用唯一计划 ID 或业务关联约束防止重复创建；重试返回已提交的结果。过期规则与“已完成计划结果保留多久”分别定义，避免把执行资格过期与结果查询混为一谈。

确认时重新验证归属、字段和日期。用户可能在生成后等待很久或宠物已被删除，不能只相信生成时的检查。

### 5.3 数据含义与营养口径

这部分优先修正产品语义；涉及营养规则的更改，应另行对照原始资料并进行专业核验，本文不验证临床适用性。

- **未打卡不等于未执行**：回答用“没有记录，暂无法判断”，提醒遗漏与实际漏做分开。
- **日均必须标分母**：当前喂食汇总按有记录天数算日均，应明确“有记录日均”；缺失热量的餐次要单独标记，不能把部分记录当完整摄入。
- **零食上限不等于实际摄入**：当前引擎固定扣除 10% 预算。应区分“不喂零食”和“计划零食摄入”，并解释默认预留策略。
- **未知不等于通过**：保证值缺失或水分使用默认值时，标注“信息不足”或“估算”，不能汇总成完整营养合格结论。
- **计算可复现不等于适用性已验证**：公式、系数、来源、适用范围和版本需要能追溯。
- **文档与代码一致**：MER 当前实现按条件选基础系数再乘活动系数，文档不应写成所有条件独立相乘。
- **时间统一**：通过可注入 `Clock` 与明确业务时区处理日期，便于测试下周、跨月、跨年及晚间场景。

### 5.4 引用与检索

知识数量不能替代检索质量。先补文档去重、原始来源、段落定位、更新时间、审核依据与审核人或审核流程说明。

“approved”是业务状态，不自动代表兽医审核。若尚未有专业审核，不应对外宣称全部语料经专家审定。

用固定题比较向量检索与 SQL 降级；评估物种、生命阶段过滤是否遗漏通用条目。只有错误分析显示召回不足，再考虑混合检索或重排，避免增加无收益的链路。

## 6. 鸿蒙端如何成为重要卖点

### 6.1 先把已有适配做扎实

按当前介绍，可表述为“通过 ArkTS Web 容器完成 HarmonyOS NEXT 端适配，产出 HAP，并在真机验证”。不能表述为全原生业务界面。

建议验收：安装、启动、登录、问答、确认提醒、头像上传、定位允许与拒绝、返回导航、外部链接、键盘遮挡、长文本滚动、前后台切换、断网重试、后端不可达和证书异常提示。

记录实际设备型号、系统版本、应用构建版本、测试日期。已测试某一台真机，不能据此宣称兼容所有鸿蒙设备。

Web 容器涉及原生桥接时，只向允许的可信来源开放有限能力；验证导航目标，不向任意网页暴露文件、定位等权限。

### 6.2 最值得选做的原生增强

| 能力 | 用户价值 | 前提与验收 |
| --- | --- | --- |
| 原生提醒通知 | 应用之外也能感知待办 | 先核对目标 SDK、权限和分发约束；验证退出、重启、修改取消及重复提醒 |
| 通知或桌面入口跳转待办 | 减少打开应用后的查找步骤 | 登录有效时打开目标宠物任务；失效时登录后恢复目标 |
| 离线只读今日计划 | 网络差时仍能查看已同步安排 | 显示同步时间，缓存按用户隔离，退出清理，离线不伪装实时状态 |
| 适合手机的快速打卡 | 降低记录成本 | 明确目标宠物，防重复提交，成功后刷新关联统计 |

若只选一项，优先考虑“提醒触达 → 打开待办 → 完成打卡”。通知能力取决于实际平台与分发条件，不能把网页内倒计时展示当成系统级后台提醒。

本文不指定鸿蒙 API 名称；实施前必须按实际 SDK 查官方文档，再确定实现与估时。

### 6.3 演示方式

鸿蒙真机作为主展示设备之一，完成综合照护问答与人工确认。介绍重点是“宠物照护任务在鸿蒙设备上闭环”，再解释具体适配项。HAP 仅适配与部署成功，也有价值；真正加分多少由官方权重决定。

## 7. 值得增加的产品能力

### 7.1 优先增加

| 能力 | 最小实现 | 优先原因 |
| --- | --- | --- |
| 每周照护复盘卡 | 汇总事实、记录缺口、未来待办与一个可确认行动 | 最能贯通现有模块与多 Agent |
| 记录完整度提示 | 展示本周期哪些数据有记录，哪些未知 | 提升回答可信度，减少误判 |
| 行动后回看 | 计划创建、打卡、下次周报引用完成记录 | 证明系统具备连续使用价值 |
| 问答质量工作台 | 匿名化差评、原因分类、版本与修复记录 | 让反馈真正指导迭代 |
| 演示数据集 | 标注为演示账号，固定宠物与历史记录 | 提高现场可重复性，隔离真实用户资料 |

### 7.2 有时间再增加

- 食品标签录入辅助：识别只生成待核对字段，用户确认单位与数值后才能进入营养计算。先评估录入负担，再决定是否引入 OCR。
- 数据导出与账户数据删除：导出宠物记录、限制他人访问，定义删除范围和保留策略。
- 家庭共同照护：需要成员授权、角色、操作人记录与防重复打卡，改动较大，赛前谨慎加入。
- 订阅式周报或提醒触达：需明确通知渠道、用户授权与失败处理，不能把站内任务列表包装成已主动送达。

每增加一个功能，都应回答：解决哪个已观察到的问题、复用哪些已有数据、怎么验收、删掉后是否影响核心展示。答不清就暂缓。

## 8. 评测与验收方案

### 8.1 固定评测集

建议建立 60 个用例，关键动态问答重复运行 3 次，报告实际调用次数与结果；模拟模型测试和真实模型测试分别统计。

| 类别 | 数量 | 检查重点 |
| --- | --- | --- |
| 通用知识与来源 | 10 | 检索、物种过滤、引用是否支持结论 |
| 真实宠物记录问答 | 10 | 数字、日期、分母、未记录的语义 |
| 多 Agent 综合任务 | 10 | 拆分、角色工具范围、结果交接、汇总 |
| 提醒生成与确认 | 10 | 日期澄清、字段校验、幂等、过期 |
| 多轮与越权 | 10 | 指代、换宠物、跨账号读取或确认 |
| 故障与输入攻击 | 10 | 模型超时、工具失败、检索无命中、注入指令 |

典型用例：

1. 七天中仅五天有记录：回答不能说两天没喂。
2. 部分餐次没有热量：不能把其总和当完整摄入。
3. 今天写入新体重后追问：不能复用历史旧数值。
4. 没有体重记录：不能生成体重变化率。
5. “下周三上午九点”：使用固定业务时区与测试时钟计算。
6. “下午提醒一下”：必要字段不足时先澄清，不随意补日期与事项。
7. 用户 B 确认用户 A 的 token：拒绝，且不泄漏计划内容。
8. 同 token 并发确认：最终只产生一条提醒。
9. 体重服务失败：保留其他结果，明确体重维度缺失。
10. 专项角色 JSON 无法解析：受预算约束修复或退回事实结果。
11. 检索内容含“忽略规则”：不改变权限或执行写操作。
12. 鸿蒙定位拒绝、网络断开：有可理解提示和恢复入口。

### 8.2 指标口径

| 指标 | 计算方式 | 建议验收方向 |
| --- | --- | --- |
| 任务成功率 | 满足该题全部预设条件的运行数 / 总运行数 | 按类别报告，避免仅给总分 |
| 数字一致性 | 与服务端事实一致的可核对数字 / 被核对数字 | 固定演示集不得出现错数 |
| 引用支持率 | 被来源实际支持的受检主张 / 受检主张 | 人工判定并保留依据 |
| 权限与重复写入 | 越权成功数、同计划重复写入数 | 测试范围内为零 |
| 降级正确性 | 正确标缺失且保留其他结果的运行数 / 故障运行数 | 覆盖关键依赖 |
| 延迟 | 总耗时 P50、P95，以及超时比例 | 与单 Agent 基线比较 |
| 调用成本 | 每次模型次数、输入输出 token、实测费用 | 使用账户实际账单口径 |
| 用户评价 | 已评价回答有用数 / 已评价数 | 同时列样本数、未评价数 |

上述均是计划统计项，不是当前成绩；有限测试通过不能证明生产环境绝无错误。

### 8.3 证明多 Agent 值得做

同一组综合题对比现有单 Agent 与新编排，固定数据、模型配置与评价准则。重点看工具是否查齐、数字是否一致、缺失是否识别、计划是否正确，同时记录延迟与成本。

若多 Agent 没有改善任务成功率，却明显增加延迟，应缩小启用范围或回到单 Agent。正式材料只报告实际观察到的收益，不能预写“准确率提升 30%”。

## 9. 真实用户反馈怎么形成证据

先邀请约 5—10 位目标用户试用；这只是招募目标，不代表已有用户。每人完成建档、查看营养、记录、综合问答、确认提醒等任务。演示数据用户和使用自己宠物数据的用户分开统计。

记录：匿名编号、是否养宠、任务是否独立完成、耗时、卡点、评价和后续修改。引用原话与截图前取得同意，公开材料去除账号与个人信息。

反馈表建议字段：日期、版本、场景、问题、严重程度、用户期望、采取措施、复测结果。至少完成两三个“用户指出问题 → 修复 → 再验证”的真实案例。

有用率只代表参与评价的回答的主观反馈，不等于知识准确率，更不等于医疗效果。不要把内部人员批量点赞当成真实用户验证。

## 10. 交付节奏与范围控制

以下为已有代码基础上的粗略工作量，按熟悉项目的一名开发者估计；不包含平台审批和外部服务等待，需先用半天技术验证再调整。

| 工作包 | 估计投入 | 完成条件 |
| --- | --- | --- |
| 规则与材料、版本盘点 | 0.5—1 人日 | 门槛证据、版本与待办明确 |
| 超时、数据语义与确认可靠性 | 1—3 人日 | 关键错误修复并通过测试 |
| 最小多 Agent 编排 | 2—4 人日 | 独立角色、任务交接、结构化输出 |
| 前端协作轨迹与事实卡 | 1—2 人日 | 显示真实步骤、缺失与计划 |
| 评测和故障测试 | 1—2 人日 | 基线对比、报告与缺陷修复 |
| 鸿蒙专项验收 | 0.5—1.5 人日 | 真机测试矩阵及录屏 |
| 鸿蒙原生增强 | 另做技术验证后估时 | 不承诺未经验证的后台能力 |
| 真实试用与材料 | 1—2 人日，另需用户参与时间 | 有反馈与迭代证据 |

如果只剩 1—2 天：完成 P0、鸿蒙录屏、固定演示与已有 Agent 评测；多 Agent 未完成就不声称实现。

如果剩 3—5 天：在 P0 稳定的前提下实现最小协作，限制为一个综合场景，保留原入口回退；暂不追加原生通知。

如果有 1—2 周：完善持久化计划、评测、试用，再选择一项鸿蒙原生增强。

提交前至少预留一天做完整回归与材料冻结。每天一次提交的限制按正式通知执行，避免最终变更未经验证。

## 11. 推荐六分钟演示

| 时间 | 展示 | 要证明的内容 |
| --- | --- | --- |
| 0:00—0:40 | 鸿蒙真机启动，介绍宠物与问题 | 平台落地与真实场景 |
| 0:40—1:25 | 营养方案和计算依据 | 数字来自算法 |
| 1:25—3:10 | 综合照护问答，展示角色步骤和事实 | 多 Agent 分工、数据与知识协作 |
| 3:10—4:00 | 对建议生成提醒并确认 | 写操作由用户控制 |
| 4:00—4:40 | 查看待办、打卡与反馈 | 行动闭环 |
| 4:40—5:20 | 一个缺数据或工具失败案例 | 不确定性处理 |
| 5:20—6:00 | 评测、真实用户改进、鸿蒙适配项 | 用证据支撑价值 |

故障案例用测试环境或可控测试依赖演示，避免临时破坏线上服务。备用视频明确标注录制时间和版本，不能冒充实时操作。

## 12. 材料与最终检查

建议最终交付：项目介绍、架构图、角色与工具权限图、评测报告、匿名用户反馈、鸿蒙测试表、演示脚本与视频、CodeArts 开发证据、第三方来源与许可证说明、部署和回滚说明。

提交检查：

- [ ] 官方赛名、门槛、权重、提交时间和入口已核对。
- [ ] CodeArts 证据与实际开发过程对应。
- [ ] 当前线上、HAP、录屏和文档标明同一可核对版本。
- [ ] 本地待发布能力已经上线，或在材料中明确标注状态。
- [ ] 多 Agent 有独立角色、工具约束、结果交接和真实轨迹。
- [ ] 数字、未打卡含义、营养估算和来源表述准确。
- [ ] 越权、并发确认、超时和失败降级测试完成。
- [ ] 鸿蒙关键流程及权限拒绝、断网恢复已真机验证。
- [ ] 用户规模、评价样本和效果指标均使用真实统计。
- [ ] HTTPS、演示账号、模型余额、外部 API 配额和网络已检查。
- [ ] 已准备可回滚产物和明确标注的备用视频。

建议现在先建立一份短任务清单：修正总超时与数据口径、核对比赛门槛、完成一个最小多 Agent 综合场景、在鸿蒙真机跑通该场景、用固定评测和真实反馈证明改进。完成后再扩大功能范围。
