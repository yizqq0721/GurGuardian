## 3. 提交与证据要求

### 3.1 必须留存的开发证据

- 码道 CodeArts 的 **AI 对话截图**（体现需求 → 生成 → 修改 → 验证的过程）。
- **IDE 日志**（构建、运行、调试、报错与修复）。
- **开发过程录屏**（从零搭建或关键功能实现，能看出是团队自己做的）。

### 3.2 建议随作品提交的材料

- 项目简介（一页）：定位、痛点、核心场景、亮点。
- 架构图：前端、后端、数据库、向量库、外部 API、Agent 工具链。
- 演示视频或现场演示脚本（3–8 分钟）。
- 功能清单与完成度说明（哪些已上线、哪些是规划）。
- 安全与边界说明（尤其是宠物健康场景的免责声明）。
- 线上地址与演示账号（如允许公开）。
- 代码仓库地址与依赖 / 开源协议说明。

### 3.3 提交节奏建议

- 每天最多一次提交，**不要卡点提交**；提前半天完成构建与冒烟。
- 提交前确认：线上版本 = 演示版本 = 材料里写的版本。
- 保留上一版可回滚产物，防止当天提交后发现严重问题。

## 6. 评审视角下的项目亮点（答辩可直接用）

1. **不是「大模型算命」**：热量、克数、营养达标全部由公式和国标计算，模型只负责组织语言。
2. **Agent 有真实数据**：模型自己决定查体重、喂食、提醒还是知识库，回答里的数字都能对上数据库。
3. **回答可溯源**：知识问答逐条附来源；工具回答展示「已查询」轨迹。
4. **写操作可控**：AI 只生成计划，服务端保存并绑定用户，用户确认后才落库；重复确认幂等，伪造 token 无效。
5. **失败也说清楚**：工具异常时明确告诉用户「哪项数据没取到」，并禁止模型补数字；模型超时自动回退检索问答。
6. **反馈不是摆设**：评价会汇总成有用率与差评清单，能指导知识库和 Prompt 迭代。
7. **两个 Agent 有真实分工**：周度复盘里分析 Agent 只查事实和缺口，计划 Agent 没有数据工具、只能基于分析结论提建议并提案提醒；交接由工具范围强制保证，不是同一条 Prompt 演两次。
8. **多端可演示**：Web、Android APK、鸿蒙 HAP 共用同一套后端。

## 7. 答辩可能被问到的问题

| 问题 | 建议回答要点 |
| --- | --- |
| 这和直接问 ChatGPT 有什么区别？ | 数据来自用户宠物档案与打卡记录；知识来自经来源标注与入库筛选的语料；数字由确定性算法计算；每条回答可溯源 |
| 模型编数字怎么办？ | 系统提示禁止编造；工具失败时禁止给出该维度数字；营养数字不经过模型；回答附来源 |
| AI 能不能自己创建提醒？ | 不能。AI 只生成待确认计划，服务端保存 10 分钟，用户确认后才落库 |
| 多轮对话怎么实现？ | 会话落库，取最近 8 条 / 1500 字注入上下文；指代靠历史，事实必须重新查工具 |
| 权限怎么做的？ | token 存 Redis、统一拦截、资源归属校验、管理员角色、写操作人工确认、token 绑定用户 |
| 为什么不做诊断？ | 宠物医疗属受监管领域；产品定位是营养管理与就医决策辅助，主动讲清边界 |
| 多 Agent 为什么没做？ | 已经做了：周度照护复盘是「分析 Agent → 计划 Agent」顺序协作，工具集隔离，计划 Agent 没有数据工具、只能吃分析结论；没有做的只是动态任务规划与并行执行，因为当前场景顺序两步即可闭环，多加角色只会增加延迟与不确定性 |
